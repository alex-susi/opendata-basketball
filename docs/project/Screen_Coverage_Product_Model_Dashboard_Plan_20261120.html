1. Scope, assumptions and release milestones

Planning assumptions

  • First workflow: coach/scout film review, with a pause-and-reveal replay. Player training follows from the same foundation.
  • First screen scope: supplied screen events and four participant identities. Automatic screen identification is a later, separately evaluated phase.
  • Model testing: staged comparisons. Test the three individual changes before spending full compute on combinations.
  • Format: short tasks for implementation, with coach-facing purpose, exact file targets and acceptance checks. These assumptions remain editable; no clarification selections were received.

Definitions to keep consistent

  • Forecast: probability of the screen’s single recorded event-level label, using tracking available by the current frame. “Eventual” does not necessarily mean the possession’s last defensive arrangement.
  • Developing read: an updated forecast of that same label. It is not a supervised label for every intermediate defensive state.
  • Recorded coverage: the provider’s retrospective event label. Reveal it deliberately; do not treat it as known at the pick marker.
  • Pick marker: picks.frame; a supplied reference point, not proven contact or a universal decision deadline.
  • Coverage scope: over+show, over+drop, under+drop, under+show and switch. ICE/blitz and newly described subtypes are outside demonstrated five-class performance.

Three layers to keep separate

  • Coverage forecast: what event-level label is likely, including before the defense has completed the action.
  • Observed cues: measured depth, route evidence, approach/recovery motion and separately validated exchange flags available now.
  • Recorded label: the retrospective annotation revealed for review; it does not describe every earlier frame.
  • Scope limit: #2, #4 and #5 improve event-level probabilities. They do not create a complete current-state classifier without additional definitions, labels and validation.
  • Communication: “Switch favored” can be an early forecast. “Exchange detected” needs a separate tested rule; neither should be called a confirmed fact merely because probability is high.

Video framework: coordinated actions, not one geometric label

  • Depth: screener’s defender is low, at the screen’s level or high.
  • Navigation: on-ball defender goes over or under when the screen is engaged; allow not-engaged or unclear cases.
  • Assignments: defenders recover to original matchups or exchange responsibilities.
  • Pressure: a brief approach, sustained containment or aggressive hedge can precede recovery or exchange. Switching can occur from different depths and routes.
  • Role names: use “screener’s defender,” not “hedge defender” or “big,” in the UI. Court role is distinct from the guard/wing/big personnel inputs.

Extend the review-case schema

  • Identifiers: game, possession, event, role/player IDs, reviewer, source, uncertainty and provider label. Human review describes visible behavior; intent remains an inference.
  • Components: initial-depth descriptor; guard route with not-engaged/unclear options; approach, recovery and exchange-evidence intervals.
  • Patterns: pressure_return, containment_return, pressure_exchange, at_level_emergency_exchange, denial_countered or unclear. These are review tags, not new training classes.
  • Timing: separate first evidence, persistence completion and user decision interval. Store unavailable observations as missing, not “no contact” or “no recovery.”
  • Leakage boundary: reviewed future patterns may define diagnostic groups or later targets; they must never enter a forecast before their evidence is available.

What the current tracking cannot show directly

  • The transcript highlights hand contact, shoulder orientation, deliberate collisions and verbal coverage calls.
  • The current position/movement inputs do not directly measure those cues; motion direction is not body facing and proximity does not establish contact.
  • Mark these cues unobserved unless suitable verified data are available. A tracking animation alone cannot supply a hand-contact or shoulder-orientation label.
  • Actual screen-angle changes may require body-orientation data. Player repositioning and handler-path changes are observable proxies, with different meanings.

4. Repair timing, episode ownership and data availability

Separate four different windows

  • Diagnostic extraction: inspect approximately −3:+3 around each marker to study timing and censoring.
  • Prediction domain: retain −2 start for controlled comparisons; assess extending eligible recognition toward +2 after boundary review.
  • Input history: keep the existing 1.6 seconds for the architecture experiments. Extend raw buffers consistently for later predictions.
  • Scoring/alert times: defined separately by the evaluation policy. They must not enter the network as future time-to-screen information.

Correct the descriptive anchors

  • Rename “contact” to closest H–S point in outputs and docs.
  • Compare the current ±0.48 search with wider predeclared spans; report minima at boundaries, not just medians.
  • Compare handler–screener approach with screener–defender/path geometry and the reviewed execution intervals.
  • Report approach censoring and missing proximity crossings by coverage and game.
  • Keep retrospective anchors in diagnostics. A feature used in a prediction must have a separate, past-only definition.

Create per-time eligibility and episode rules

  • Build each row using the history available by that prediction frame. Do not require complete future tracking to include an earlier forecast.
  • Preserve the old cohort for reproduction; separately report expanded eligible rows and a common-cohort model comparison.
  • Use the existing canonical possession-boundary repairs. Flag touch end separately; it is not automatically the end of a useful switch read.
  • For the live-style selected action, stop or transfer ownership at a predefined observable new action. For retrospective follow-up, retain the original event identity and label it clearly.
  • Record missingness, camera-detected versus estimated positions, history sufficiency, role consistency and the reason a forecast is unavailable.

Reuse depth features; do not turn them into hard coverage rules

  • The audited feature set already contains relative positions, velocity, lvl, lvl_v and lvl_hold. Reuse them for depth and movement displays.
  • Avoid adding a duplicate low/medium/high input as the first change. A continuous depth measurement plus motion already carries much of this information.
  • Positive level does not establish show, and at-level positioning does not establish switch. Geometry is a cue; recovery/exchange behavior supplies additional evidence.
  • Compute model depth against information available at that frame, not a future tag-anchored screen position used only in descriptive EDA.

Make switch timing causal when it is used online

  • Keep existing one-sided and future-to-window-end proxies as retrospective diagnostics only.
  • Define a finite trailing confirmation interval; compare predeclared 0.2 and 0.4 seconds.
  • Check both H–SD and S–BD exchanges, with clear distance/assignment evidence. Audit temporary-show and help false positives.
  • Time an alert at completion of the persistence interval. Never backdate a live alert to an onset discovered later.
  • Keep detection failures and unconfirmed switches in denominators. A missing proxy does not prove a wrong coverage label.

Audit other availability assumptions

  • Test prior-coverage availability at 0/1/2/3 seconds and after episode completion, plus a context-free control. These are availability sensitivities, not a search for the best-scoring delay.
  • Fit normalizers and learned personnel mappings inside the appropriate training partition. Distinguish historical external profiles from information derived later in the game.
  • Test small tag shifts, such as ±0.08/±0.16/±0.24 seconds, without choosing the shift that improves model scores.
  • Keep provider-label-only exclusions explicit. Never use a future true coverage label to manufacture a live availability or rejection decision.
  • Document that past-only feature code does not, by itself, establish that provider-supplied tracking or event annotations are available in a live feed.
Done when: each forecast has a stable event identity, auditable available-past inputs and explicit eligibility; retrospective timing proxies are separated from online rules.

Freeze an evaluation policy

  • Start with the audit’s transparent −1≤t<0 equal-weight joint loss as a provisional checkpoint benchmark. The timeline review may justify a different predefined decision anchor before architecture comparisons.
  • Publish the old main/narrow/flat scores unchanged. Do not replace one unsupported utility curve with another.
  • Score frames within each event, then events; report game-level results and whole-game paired intervals. Do not treat frames as independent samples.
  • Report time-specific and common-cohort views. Later survivors can have a different class mix; do not call an easier later sample model improvement.
  • Write thresholds, persistence, tolerated calibration/recognition degradation and comparison rules before inspecting final results. There is no established universal 0.01 loss threshold.

Two different clocks for a switch

  • Forecast clock: first stable probability-based alert for the event-level switch label. It can occur before the defenders exchange.
  • Exchange-evidence clock: first independently reviewed evidence and the later completion of a finite confirmation rule.
  • Report each clock against the relevant decision/evidence interval. Never measure an early forecast as if it proved a completed exchange.
  • A late emergency switch can legitimately remain uncertain beforehand. Evaluate probability calibration and usefulness rather than requiring early certainty.

Grade emergent decisions without inventing early certainty

  • Keep the single provider target for event-level scoring. Do not relabel a pre-switch frame as show merely because the eventual switch has not yet happened.
  • In emergency exchanges, assess calibration and lead time relative to reviewed evidence and decision intervals; retain late and never-detected cases.
  • A high switch probability does not establish that the defenders have exchanged already. Score a current-exchange detector against its own reviewed evidence, separately.
  • Use full eligible held-out events for overall precision/recall. The deliberately enriched 40–60-play sample supports case diagnosis and label checks only.

Compare checkpoint selection fairly

  • Keep architecture, seeds, sampled training frames, row policy and compute matched.
  • Save candidate checkpoints across epochs; compare main, flat and pre-marker stopping using validation data only.
  • Use the same full validation grid or explicitly identical thinning across policies. The current coarse grid slightly changes the main curve’s effective weight.
  • Keep four-seed ensembles for final comparisons. Separate improvements from extra seeds, changed eligibility and changed selection policy.
  • Save per-event/per-time validation and held-out probabilities, rather than relying on rounded aggregate curves.

Control model selection with only ten games

  • Hold out complete games. All preprocessing for a scored split must respect its training boundary.
  • Use grouped inner validation for architecture and alert-policy choices. Keep outer test-game predictions out of selection.
  • Screen predeclared variants with a modest paired-seed budget and more than one validation-game rotation; freeze finalists before full runs.
  • If reporting a selected-model pipeline, select the variant inside each outer training set. Record fold-specific selections and use the same refit rule for baseline and candidates.
  • The games have already informed development. State that limitation; do not claim a newly untouched final test from the same repeatedly inspected data.

Calibration and alert rules

  • Begin with full probability displays and a neutral uncertain state. A leader need not trigger an alert.
  • Select any temperature calibration, class thresholds, probability-gap rule and persistence on inner validation; freeze them for outer scoring.
  • Compare models at matched false-alert rates or precision where feasible. Always also report misses and detection delay.
  • Keep canonical forecasts unsmoothed initially. If a causal display smoother is added, evaluate its calibration, delay and changes separately.
  • A persistent alert is a display state, not ground truth. Show its timestamp separately from the current probability leader.
Done when: one evaluator produces reproducible probability, timing, alert, eligibility and calibration reports for the unchanged model, with a frozen selection policy.

#4 · Let the defenders’ responses depend on each other

Change and purpose

  • The defenders already share information and switch probability. The remaining restriction is independence between under/over and show/drop, conditional on inputs and no switch.
  • Keep switch probability s and under probability u; replace one show probability with h_over and h_under.
  • Retain the switch-only personnel branch. Expand the non-switch branch from two logits to three.
  • Train using joint likelihood. At inference, compute all routes; do not feed the true over/under label to the network.
  • Initialize both new show outputs by copying the old show weights and bias. Confirm identical probabilities before training.
#4 probability formulas and required checks
P(over, show)  = (1-s) * (1-u) * h_over
P(over, drop)  = (1-s) * (1-u) * (1-h_over)
P(under, drop) = (1-s) * u * (1-h_under)
P(under, show) = (1-s) * u * h_under
P(switch)      = s
  • Verify all five probabilities are finite, nonnegative and sum to one; derive defender marginals from joint sums.
  • Verify old-model equivalence after cloned initialization and gradient flow to both show branches.
  • Update saved-model schema, loss, loaders, prediction tests and exports together.
  • Assess joint/defender loss and sparse under+show behavior; do not expect this change alone to solve late switch evidence.

What the video supports about #4

  • Holding the screen level while the guard recovers describes coordinated guard/big behavior.
  • #4 allows the show probability to depend on over versus under after no switch; it does not add intermediate-state supervision.
  • The basketball rationale supports testing the constraint. It does not establish that removing it will improve held-out forecasts.

Recognition candidates from the video

  • Pressure/return: describe a past approach toward the handler followed by movement back toward the screener.

Optional B2R: explicit exchange-gap and recovery summaries
handler_gap = distance(H, BD) - distance(H, SD)
screener_gap = distance(S, SD) - distance(S, BD)
  • Roles: H = handler, S = screener, BD = original handler defender, SD = original screener defender.
  • Positive gaps place each attacker closer to the alternative defender. They are geometry consistent with an exchange, not proof of matchup responsibility.
  • Use finite trailing duration and relative movement; audit temporary shows, help and crossing paths as false-positive controls.
  • For approach/return summaries, use only samples up to the query frame. Never use eventual recovery time, a future minimum or persistence to the end of a future window.
  • These are derived from existing tracking information. Normalize inside training folds and measure whether the explicit representation helps.

Drop and containment: optional reviewed geometry

  • The video’s drop read includes protecting the basket while containing both handler and roller. Depth alone does not fully describe that task.
  • For film review, inspect the screen defender’s relationship to the current handler-to-basket and screener-to-basket paths, using only current positions.
  • If those cues explain persistent errors, test path-relative containment/recovery features later with the deferred help/lane work. Keep them out of the initial B4/B2/B5 comparisons.
  • A geometric path is a descriptive approximation, not proof that the defender can stop a drive or that he physically contacts the attacker.

Checks and display connection

  • Check geometry against raw coordinates, including stationary players and near-zero distances; define closing speed consistently.
  • Changing unavailable future frames must not change present pair features or predictions.
  • Test temporary-show controls and both sides of an exchange, not just the big approaching the handler.
  • Export measured distances/motion for an optional Observed cues panel. Describe measurements rather than claiming a model-causal explanation.
  • Measure early switch probability quality, later detection delay and false alerts. Add typed pair tokens only as a later, separate variant if warranted.

Export and loader contract

Proposed display/export namespaces

  • forecast: event ID, query frame, model/policy IDs, eligible flag, five probabilities and alert state.
  • observed_cues: current depth, pair distances/motion, masks, availability frames and separately versioned experimental flags.
  • recorded: provider event label, review-pattern tags and crosswalk provenance; accessible through deliberate review/reveal behavior.
  • Keep these responsibilities separate even if files are bundled for efficient loading. None of the recorded fields may select or modify a forecast.

Version the data rather than guessing formats

  • Add schema version, model/config/policy identifiers, frame rate, label order and held-out-game provenance.
  • Export frame-aligned probabilities at sufficient precision, per-time eligibility/reason, action IDs/bounds and available-past cue fields.
  • Keep recorded labels logically separate from forecast fields; reveal logic must never read them to choose the active forecast.
  • For the ten replay games, export held-out-game predictions. A model refitted on all ten for new games must stay separate and must not overwrite those out-of-game evaluation forecasts.
  • Keep full-precision scoring outputs; validate export rounding. Support the legacy schema or regenerate assets together; fail visibly on a schema mismatch.
Done when: a user can find a relevant screen, open it before execution, follow a clear forecast on desktop/mobile and reveal the recorded outcome without accidental future information.

Extend the export contract for cues and review tags

  • Keep event-label probabilities, recorded labels, frame-level measurements and review-pattern metadata in separate named fields.
  • For each cue/flag, record units, method/version, availability frame, missingness and—where relevant—persistence-completion time.
  • Make observation time explicit so the client cannot display a completed return or exchange before it was measurable.
  • Store label-crosswalk/review provenance separately. Reviewed future metadata must not alter current forecast eligibility, event selection or model inputs.

What earns promotion

  • A repeatable improvement in the predefined primary forecast measure, with acceptable calibration, recognition, false-alert and latency tradeoffs.
  • A concrete user benefit: earlier useful warning, fewer misleading reads, clearer uncertainty or a materially easier scouting task.
  • All numerical, past-only, export and dashboard checks pass. Inspect confident mistakes as well as successes.
  • Preserve the previous model, public assets and schema adapter. Make rollback a recorded release operation.
  • Update the site’s Model documentation and decision log around the actual final change and its limits. Model export and site publication are separate implementation steps.

Later phase A · Player training

  • Reuse selected-screen replay, hidden labels and past-only traces for pause-and-predict exercises.
  • Let players choose a coverage or probability estimate, then reveal the full action and recorded label.
  • Organize drills around concrete cues and comparable possessions; include uncertain and deceptive shows.
  • Test whether the player understands the cue and can apply it to a new clip. Do not claim improved on-court outcomes from model accuracy alone.

Later phase B · Automatic upcoming-screen identification

  • Build a candidate-screen/participant stage from ongoing tracking; a simple geometric candidate generator is a valid first baseline.
  • Include non-screens, slips, handoffs, re-screens and aborted actions. Evaluate false candidates, missed screens, participant errors and warning lead time.
  • Run coverage prediction on those candidates using their identities as known then, rather than eventual annotation roles.
  • Score the complete pipeline, including failures to identify a screen. Validate the timing availability of tracking, matchups and personnel context.
  • Only then make a stronger continuous/live-use claim. Additional games and ICE/blitz examples support expanding beyond the current five classes.

Later phase C · Additional basketball hypotheses

  • Help geometry: aggressive pressure increases recovery demands. Test support positioning/roll-lane relationships only after the core comparisons; retain all ten players in the model.
  • Personnel/scouting context: a prior permitted shooting profile may help explain coverage expectations. Use genuinely historical information, not the outcome of the same play.
  • Weak-hand denial: require verified permitted handedness; respect coordinate reflections. Without it, describe forced direction, not weak-hand intent.
  • Richer state outputs: first define and review phase labels. If a current-state display proves useful, evaluate a transparent rule or auxiliary/state model separately; #2/#4/#5 alone do not create it.
  • New coverage classes: expand only after resolving terminology, adding adequate examples and validating across games. Coaching concepts motivate hypotheses, not automatic model complexity.
First implementation task
  • Freeze the current release, then prototype explicit screen selection, reveal controls and the mobile coverage panel.
  • Use that prototype for the 40–60-play timing review before fixing the new evaluation policy or changing the model.
